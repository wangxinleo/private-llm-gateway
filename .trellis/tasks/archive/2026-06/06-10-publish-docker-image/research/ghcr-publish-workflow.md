# GHCR Publish Workflow Research

## Question

How should this repository publish a Docker image automatically from GitHub Actions?

## Sources

- GitHub Docs: Publishing Docker images — https://docs.github.com/en/actions/use-cases-and-examples/publishing-packages/publishing-docker-images
- GitHub Docs: Automatic token authentication — https://docs.github.com/en/actions/security-for-github-actions/security-guides/automatic-token-authentication
- Docker Docs: GitHub Actions with Buildx — https://docs.docker.com/build/ci/github-actions/
- Docker metadata-action — https://github.com/docker/metadata-action
- Docker build-push-action — https://github.com/docker/build-push-action

## Findings

- GitHub Actions can publish to GitHub Container Registry using the built-in `GITHUB_TOKEN` when the workflow grants `packages: write`.
- The standard GHCR target format is `ghcr.io/<owner>/<image>`.
- Docker's common GitHub Actions pattern is:
  - checkout source
  - set up Buildx
  - log in to `ghcr.io`
  - generate tags and labels with `docker/metadata-action`
  - build and push with `docker/build-push-action`
- Pull requests should normally build but not push images, because PRs can come from untrusted forks and do not represent releasable code.
- Branch pushes can publish a moving branch tag, and tag pushes can publish immutable version tags.
- The repo already has a working `Dockerfile` that builds a Next.js standalone image, so the CI change can focus on workflow orchestration rather than Dockerfile design.

## Recommended MVP

Publish Docker images to GHCR only for trusted refs:

- On push to `master`: publish `ghcr.io/<owner>/privacy-proxy:latest` and a branch tag.
- On Git tags shaped like `v*`: publish semantic version tags generated by `docker/metadata-action`.
- On pull requests: run tests and Docker build validation, but do not push.
- Keep the existing Node test/build job, and add a separate Docker image job after it succeeds.
